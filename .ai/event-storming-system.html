Notes & Assumptions

  • Actors: "Admin" and "Installer" are inferred from REST API endpoints. The system assumes these roles interact via HTTP controllers.
  • External Systems: "Work Order System" and "IoT Device" are inferred from the domain context. Work orders are received from an external system, and IoT devices communicate via IoT16/IoT20 protocols.
  • Device Configuration Aggregate: The aggregate encapsulates device configuration state and emits domain events for all state changes. The patch command can trigger multiple change events depending on what fields are updated.
  • Installation Aggregate: Represents the installation workflow lifecycle. The aggregate enforces business rules at each phase transition and emits events for state changes.
  • Boot Notification: Boot notifications are received from IoT devices via CommunicationService, which publishes Spring application events. The Installation aggregate registers these boot notifications and requires confirmation if hardware/firmware changes are detected.
  • Optimistic Locking: The DeviceConfiguration aggregate uses version-based optimistic locking (not shown in diagram but present in service layer).
  • Read-Only Operations: Query operations (getDevice, listDevices) are not shown as they don't modify state or emit events.
  • Delete Operation: The deleteDevice command is shown but doesn't emit domain events in the current implementation (may be handled at repository level).
  • SAT Answers: The markSatAnswersComplete command is a simple state change without explicit validation rules shown in code.
